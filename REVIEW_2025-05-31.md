## 2. Five-Axis Code Review

### 2.1 Correctness

**Verdict: Good — strong mathematical guarantees, known gaps documented**

#### What's done right

- **LLM-finds-problems / Python-applies-fixes principle** is rigorously enforced. `synthesize_adjustments_node` in `review_graph.py` is entirely deterministic Python — no LLM mutation of floats. This is the single most important correctness decision in the project and it's consistently applied.
- **FCFF math** (`valuation.py:_compute_dcf_value`) is pure function with explicit parameters. Unit-tested with accounting identities (FCFF compounding, terminal value Gordon precondition).
- **Monotonicity validation** (`scenarios.py:_violates_monotonicity`) ensures bull ≥ base ≥ bear per field. Probabilities must sum to 1.0.
- **Profile priors** (`priors.py`) with hard/soft bounds per sector profile — blocks obviously wrong assumptions.
- **Convergence damping** — same-direction repeat adjustments are halved to prevent oscillation.
- **`ReviewState` isolation** — one-way snapshot from `DCFState` prevents accidental upstream mutation.

#### Gaps

| Severity | Issue | Location |
|----------|-------|----------|
| **Critical:** | Standalone DCF endpoint (`POST /workflows/dcf/runs`) HITL resume is broken — `Command(resume=...)` path may not find saved state in MemorySaver. Acknowledged in known limitations. | `server.py` |
| **Important:** | Market-implied signals incomplete — only implied WACC computed; implied growth and margin needed for deeper critique. Prevents full convergence-gate analysis. | `valuation.py:compute_market_signals_node` |
| **Important:** | `review_adjustments` sparse in fast path — when `scenario_results` is empty, `synthesize_adjustments` has no scenario deltas to apply, adjustments target base only. | `review_graph.py:synthesize_adjustments_node` |
| **Important:** | RAG into evidence layer — `documents.py` + ChromaDB exist but are unused in `assemble_evidence_node`. User uploads (PDFs of 10-K transcripts, broker notes) should feed into assumption provenance. | `evidence.py` |
| **Consider:** | `_ttl_for` returns `float('inf')` for Layer 0/1 nodes but `86400 * 30` for Layer 2 — magic numbers. Consider constants in a shared config. | `kg/cache.py` |
| **Consider:** | `_build_initial_state` validates required fields but doesn't validate horizon_years range (e.g. negative or 0 would crash downstream). | `dcf/graph.py` |

### 2.3 Architecture

**Verdict: Excellent — well-architected, strong design principles consistently applied**

#### Strengths

- **Parent-subgraph pattern** — `file.py` routes between `research.py` and `conversational.py` subgraphs, each with their own state slices. Clean separation.
- **Three compiled DCF graphs** from the same node set (`dcf_workflow_app`, `dcf_valuation_app`, `dcf_scenario_val_app`) — elegant pattern. Avoids code duplication; each graph is a subset of nodes wired differently.
- **KG three-layer model** — anchored facts (immutable), derived inferences (rebuildable, TTL), run artifacts (immutable history). Prevents Layer 3 from feeding into future runs — preserves reproducibility.
- **Append-only context stack** (Manus-inspired) — immutable, KV-cache friendly. Pointer-based tool result retrieval keeps context short.
- **Unified DCF HITL** — same tool, same events, same UI in both chat and research mode. No special-casing.
- **`kg_run_id`** separate from `parent_step_id` — correct decoupling of activity streaming from KG identity.
- **HITL snapshot restore** — `hitl_snapshot.py` preserves evidence/provenance across the approval boundary, avoiding `user_provided` provenance fallback on fast-path re-run.
- **Two-tier drill-down in KG hub** — presentation ≠ persistence. Hub nodes are React-side synthetic objects; DB schema unchanged.

#### Potential concerns

| Severity | Issue |
|----------|-------|
| **Consider:** | Single-process worker model — no DB claim lock or multi-worker coordination. If this ever needs to scale beyond one user, worker coordination will be needed. |
| **Consider:** | `MemorySaver` (in-memory checkpointing) — state is lost on server restart. Job resume on restart works for research but not for DCF standalone endpoint. Consider LangGraph's `SqliteSaver` for production resilience. |
| **FYI** | Deck `adapters/` directory exists but only has `__init__.py` — README mentions `dcf_output`, `document`, `chart_artifact` adapters but they're not visible in the directory listing. If they're inline in `normalize.py`, consider extracting them. |

### 2.4 Security

**Verdict: Acceptable for a personal research project — no major vulnerabilities detected**

#### Observations

- API keys stored in `.env` — standard and appropriate.
- `calculator` tool uses `simpleeval` (safe eval) — good, no arbitrary code execution.
- `execute_python` runs in a `subprocess` — isolated from the main process. Uses temp files.
- SEC EDGAR is free, no key needed — no credential leakage risk.
- PDF report generation (`report_export.py`) uses ReportLab — no known injection vectors.
- FastAPI endpoints use Pydantic models for request validation — input is validated at boundaries.
- CORS middleware configured — reasonable for a local dev setup.

#### Gaps

| Severity | Issue |
|----------|-------|
| **Important:** | `execute_python` tool runs arbitrary Python in a subprocess. While isolated from the main process, it has filesystem and network access (yfinance, requests, matplotlib). A malicious prompt could exfiltrate data. Consider sandbox restrictions (e.g., read-only filesystem, network allowlist). |
| **Consider:** | No rate limiting on FastAPI endpoints. A client could flood `/runs` endpoint with requests. |
| **Consider:** | No authentication layer on the API. Appropriate for local dev but would need auth for any deployment. |
| **FYI** | `pandas`, `matplotlib`, `yfinance`, `requests` are all available to `execute_python`. The user-facing risk is low (it's a local research tool), but worth documenting in security posture. |

### 2.5 Performance

**Verdict: Good — caching strategy is sophisticated, known latency issues documented**

#### Strengths

- **KG cache-first strategy** — `cache_check_node` probes for cached fundamentals, evidence, synthesis, thesis. Hits → downstream nodes short-circuit. Misses → full LLM/API path. This is the single biggest performance win.
- **TTL-based caching** per KG layer — Layer 1 infinite for filed/news, Layer 2 7-30 days for derived inferences. Appropriate.
- **Confidence floor 0.7** — below this, cache is treated as miss. Prevents stale low-quality data.
- **`user_stated` lock** — auto-writes never overwrite user-stated nodes. Prevents unnecessary re-fetches.
- **Static system prompt** — identical across all research steps, near-100% KV-cache hit on LLM calls.
- **Pointer-based tool result retrieval** — agent messages contain `tool_result_id` pointer, full payload fetched only when needed. Keeps context window small.
- **Three compiled DCF graphs** — fast path (`dcf_valuation_app`) skips evidence/synthesis/memo, runs math only.

#### Known issues

| Severity | Issue |
|----------|-------|
| **Important:** | No latency budget / telemetry — README's "Future Work" section correctly calls for per-node duration logging to run output JSON. |
| **Consider:** | `assemble_evidence_node` could benefit from parallel fetching — SEC filings, FMP API, yfinance, and web search are I/O-bound and could run concurrently. Currently appears sequential. |
| **Consider:** | ChromaDB + BM25 hybrid RAG for document search — good, but indexing runs inline during upload. Large PDF uploads could block the request handler. |
| **FYI** | `_cache_check_node` loads all anchored corpus into state — for a ticker with many years of filings, this could grow large. Corpus growth is additive-only (by design), but no compaction story yet. |

## 4. Overall Assessment

### What makes this codebase strong

1. **Architectural principles are real, not aspirational.** The three guiding principles (LLMs find problems / Python applies fixes; evidence-grounded; cache-first) are mechanically enforced in the code — not just mentioned in docs.

2. **KG three-layer model is genuinely well-designed.** Anchored facts (immutable, additive), derived inferences (rebuildable, TTL), run artifacts (immutable history, never input to future runs). This is better than most production KG designs I've seen.

3. **Test suite is pragmatic.** 400+ tests, zero LLM calls in CI, runs in ~10s. Golden dataset with hand-curated DCF records and extrapolation recipe. Honest about what's not tested.

4. **README is a true single source of truth.** Every decision, limitation, and future plan is documented. This is what "living document" should mean.

5. **HITL is deeply integrated, not bolted-on.** Per-step interrupts, assumption review with full evidence context, deck outline review, snapshot restore for fast-path re-runs.
